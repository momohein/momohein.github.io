Homie: a shared-house manager

A Spring Boot web app that lets housemates split bills, rotate chores and keep each other informed. I designed it, built it, tested it and deployed it to the cloud, and it's in daily use by a real 9-person house. Built solo as my final project at National College of Ireland.

The problem

Shared houses run on group chats and memory. Who paid the electricity? Whose week is it to clean? Which room has bins on Thursday? Housemates often come from different countries, so notices in one language get missed.

Homie puts all of that in one place. Each house has its own members, rooms, bills and rota, so any number of houses can use the same app independently.

Features

Bill splitting

Bills split equally between current housemates. Each share is tracked and ticked off one by one, and only the person who added the bill can mark shares paid.

Cleaning and bins rota

Cleaning rotates weekly through members in their chosen order. Each room gets a fixed bins weekday. Both cycles start from the house's creation date.

Reminders

A scheduled job runs at 8am every day and notifies housemates about bills due, through an in-app bell and by email.

Translation

Announcements and bill descriptions can be translated on demand by a locally run Ollama model (llama3.2), with no paid API.

Accounts and houses

Sign up and create a house, or join one with an invite code. Profile pictures, account deletion and a forgot-password flow with expiring reset links.

House admin

Rename the house, add and rename rooms, and reorder the cleaning rota.

Architecture

Homie is a layered MVC monolith. Controllers handle HTTP and pick a Thymeleaf view, services hold the business rules, and Spring Data repositories talk to PostgreSQL. DTOs carry form data so entities never bind directly to requests.

Deployment

The app ships as a Docker image built in two stages: a Maven stage compiles and packages the jar, and a slim Temurin 17 JRE stage runs it with memory capped at 70% of the container. Render builds and hosts the image, and the database lives on Supabase.

Key decisions

  • No secrets in the repo. Every credential comes from an environment variable with no real default, so the app fails loudly if one is missing instead of using a leaked value.
  • Cookie-based CSRF tokens. Behind Render's proxy the session cookie wasn't sticking and login POSTs failed with 403. Moving the CSRF token into a cookie fixed it without turning CSRF off.
  • Supabase session pooler. Render's servers are IPv4-only and Supabase's direct connection is IPv6-only, so the app connects through the pooler.
  • Plain JDK HTTP client for Ollama. Spring's HTTP helpers move between Spring Boot major versions, so java.net.http.HttpClient keeps translation working on Spring Boot 4.
  • Everything scoped per house. Rotas, bills and deletions are all queried by house, so many houses can share one database safely.

Debugging story: the silent notifications

Bill reminders weren't showing up on the bell or arriving by email, even though the query was finding the right bills and the right housemates. I added temporary logging and compared raw database values with what the UI showed until I found the real cause.

ERROR: null value in column "created_at" of relation "notifications"
violates not-null constraint

The createdDate field had no column mapping, so Hibernate tried to write created_date. The real column is created_at. Every insert failed, so the code never reached the email step.

The fix was one annotation, @Column(name = "created_at", nullable = false), which kept the Java field name so nothing else had to change. While reviewing the code I also found that deleting an account looked through every bill in the app instead of only that house's bills, and fixed it with a findByHouse query.

To demo reminders without waiting for 8am, I added a "Send reminders now" button that calls the same method the scheduled job uses.
